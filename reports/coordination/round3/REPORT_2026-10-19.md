# DabAI: отчёт координатора по раунду 3 (19.10.2026)

Цель раунда — улучшить E2E-дубляж целиком: озвучку, lip-sync, стабильность лица, требования ТЗ. Скорость — после качества.
Используются только коммерчески чистые модели. Остановлено по решению пользователя; все ветки запушены (раздел 6).

## 2. Ключевые решения пользователя
1. **GPU использовать по максимуму** на всех серверах; CPU не главное. C делит GPU с A: C ≤ 10 ГБ, A ≤ 20 ГБ.
2. **Только коммерчески чистые модели.** LatentSync остаётся: веса OpenRAIL++, код Apache-2.0, это устраивает.
   - `download_models.sh` заново скачал веса HDEMUCS на B и D. Они перемещены в `quarantine_nc/demucs`.
   - D закрыл дыру (a1d0100): скрипт больше не качает запрещённое, `assert_clean_tree()` останавливает прогон.
   - cand5 — только справочные цифры, повторно не рендерится.
3. Проверить пиковую загрузку GPU всеми моделями (пункт ТЗ про пиковую VRAM), включая Qwen на GPU.
4. После исчерпания лимита все агенты переведены на medium.

## 3. Результаты

### Озвучка (C)
- audio-r2 воспроизведён, затем сделаны **audio-r3** и **audio-r3b**.
- **Всё на GPU:**
  - Qwen Q8_0 через CUDA-сборку llama-cpp-python: 8.3 ГБ; сегментация 03 76 → 6.9 с, перевод 55 → 4.8 с; сегментация
    совпадает с CPU;
  - Spleeter портирован на PyTorch (те же MIT-веса): 400 → 1 с;
  - аудио-этап 632 → 120–227 с на минуту видео.
- Числа и единицы перед TTS переводятся в слова: «600 by 600 … 9 millimeters». Добавлена защита от дрейфа Qwen (китайские
  символы, вставки в скобках).
- Declick итеративный: 0 щелчков на проблемных местах.
- «Hamam» в 02 исправлен: WER 02 0.075 → 0.022.
- **audio-r3b:** −16 LUFS на всех видео, true peak ≤ −1.2 dBTP. Было −12.9…−20.4 LUFS и пики до −0.2 dBTP.
- Не закончен layer-3 refit поверх r3 (17 целей шли на GPU).

### Lip-sync (A)
- r2best отрендерен на audio-r2 для 01/03/04/05.
- Кандидат R3: r2best + guidance 2.0 + bridge 8x4 + не больше 400 кадров на один вызов LatentSync. Отрендерен на audio-r3,
  03 и 05 SUCCESS. A/B SyncNet против r2best на одной озвучке стоял в очереди.
- Нагрузка на CPU ограничена: A ≤ 16 ядер, C ≤ 14 (квота контейнера около 31 ядра, а не 256).
- В README A (ad7ada1) есть результаты вариантов и строки ТЗ 5.4 / 11 / 8.5.

### Лицо и композит (B)
- Мастер «точно по времени» (`DUB_MASTER_TIMING=fps`): ошибка часов 0 вместо −60 мс.
- Новые опции композита: `--colour-match upper`, `--seam-lf 4`, `--sharpen-auto`, защита губ, текстура кожи из исходника.
- На 05:
  - сползание 0.05 px (r2: 0.10);
  - мерцание цвета 0.54 → 0.38;
  - чёткость рта 0.82 → 0.91;
  - скачки на стыках окон 0.93× от внутренних кадров (у LatentSync 1.38×).
- Мосты на стороне генератора ничего не добавляют к исправлению стыков в композите. Худшие секунды — это смаз и панорамы
  камеры, а не композит.
- Полные ролики «новое лицо + озвучка C» сделаны для 01–05 (audio-r2 и audio-r3).
- Варианты «рта в паузе дубляжа»: OPT1 неподвижный, OPT2 оригинал.

### Сборка, ТЗ, GPU (D)
- r2m (все ветки r2) и r3F (r2best + композит B на audio-r2) собраны на всех 5 видео. Генератор A влит (6bded4b).
- Кандидат r3cand на audio-r3 / r3b стоял в очереди.
- **r3F против clean0:**

  | метрика | r3F | clean0 |
  |---|---|---|
  | 9.4: 30 fps | PASS на всех видео | FAIL на 03/04/05 |
  | 8.4: растушёвка | 11.4–11.5 px, PASS | 3.6–9.0 px, FAIL |
  | сползание носа | 0.05–0.13 px | 0.17–0.24 px |
  | доля скачков на стыках | 0.14–0.31 | 0.28–0.53 |
  | WER финального микса | 1–4 % | — |

  **Регрессия:** SyncNet на 05 −0.86, на 04 −0.34. Аудио в сравнении было разным, нужен A/B на одной озвучке.

- **GPU-аудит (`gpu_audit.md`, e442b5e):**

  | схема | пик VRAM | s/мин видео | результат |
  |---|---:|---:|---|
  | загрузка / выгрузка по этапам, Qwen на GPU | 22.1–24.7 ГБ | 492–511 | влезает |
  | аудио-модели + LatentSync резидентно, Qwen выгружается | 30.4 ГБ | 461–485 | влезает, запас 1.4 ГБ |
  | все модели одновременно | 31.4 ГБ / OOM | — | **не влезает** |
  | Qwen на CPU | 21.1 ГБ | 942 | влезает, в 2 раза медленнее |

  - Выгрузка работает: после закрытия Qwen видеопамять возвращается.
  - Пик растёт с длиной сегмента LatentSync. Ограничение ~400 кадров держит его около 22 ГБ, и тогда хватает карты на 24 ГБ.
  - Загрузка моделей: 51–55 с на видео.
- **Норма ≤ 300 с/мин не выполняется.**
  - LatentSync один занимает 317–342 с/мин, весь пайплайн — 460–510.
  - Дальше снижать можно только числом шагов / DeepCache LatentSync, и только с проверкой глазами.

## 4. Проблемы инфраструктуры
- Финальная выкачка раунда 2 оборвалась: на ноутбуке только 47 видео A. Видео B / C раунда 2 потеряны, код цел в git.
- Сервер A (Италия) отдаёт данные очень медленно, 25–300 КБ/с. Что сделано:
  - синхронизация разделена по серверам, загрузка в несколько потоков;
  - крупные передачи (сырой LatentSync 2.8 ГБ) отменены, B рендерит сам;
  - audio-r3b для B и D передана облегчённым пакетом (m4a + json);
  - A получает её копированием на сервере.
- Агенты упёрлись в лимит использования примерно на 2 часа; GPU в это время простаивали.
