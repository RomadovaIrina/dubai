Side finding (torch, not flash-attn) - affects anyone running fp32 attention on this box:
  torch 2.7.1+cu128 EFFICIENT_ATTENTION (mem-efficient SDPA) with **float32** inputs and 64 < head_dim <= 128
  (72/80/96/112/128 tested) returns wrong values on sm_120: max|d| vs MATH 0.06-0.6, at every length 64..4096,
  causal and non-causal. head_dim <= 64 and >= 160 are correct; fp16/bf16 are correct on every backend.
  Default fp32 dispatch selects exactly this backend (flash/cudnn refuse fp32), so plain
  F.scaled_dot_product_attention(fp32) is silently wrong for those head dims.
  Exposure in this pilot: none today - LatentSync runs fp16 on sm_120 (scripts/inference.py picks fp16 for cap > 7;
  its UNet heads are 40/80/160 so D=80 would be hit in fp32), Chatterbox runs fp16 (T3 D=64), Whisper is CTranslate2.
  Mitigation if an fp32 path is ever needed: torch.backends.cuda.enable_mem_efficient_sdp(False) (falls back to MATH)
  or run attention in fp16/bf16.

Recommendation:
  PyTorch SDPA. torch 2.7.1+cu128 already ships working fused flash kernels for sm_120 and dispatches to them by
  default; the external flash-attn 2.8.3.post1 builds and runs correctly on sm_120 but is speed-parity, costs an
  11-min source build per image, and is not required by LatentSync, Chatterbox or anything else in the stack.
  Keep flash-attn out of /venv/dabai (as today); the isolated wheel is at hand if a component later imports flash_attn.
