## Cold state definition (accepted 2026-09-20; deviation from the original harness)

- Original `ensure_stopped.sh` required the sum of **all** `/health` worker states to be 0, including `idle`/`throttled`.
- RunPod keeps one standby worker *slot* assigned to this endpoint with zero traffic (`workersStandby: 1` in the REST config). `/health` reports it as `idle` (docs: "scaled down, waiting for requests", not billed) or `throttled` (host GPU busy). GraphQL showed the slot's pod as `desiredStatus: EXITED`, `uptimeSeconds: 0`, `runtime: null`, image `ghcr.io/romadovairina/dabai-worker:v0.10.0`, machine RTX 5090.
- Attempt 1 (strict precondition, launched 19:26:14Z) never reached all-zero: the slot alternated idle ↔ throttled and run 1 hit the 900 s preflight timeout without submitting a job. It was stopped manually at ~19:44Z; no job, no reports.
- Accepted cold state: FlashBoot off · `pending_jobs = 0` · `initializing = 0` · `running = 0` · all endpoint pods `EXITED` / uptime 0 (GraphQL). A logical RunPod standby slot (`idle`/`throttled`) is not by itself a live worker/container. This is a **scale-to-zero Serverless cold container start**; it is **not** a guarantee of a fresh physical host or an empty Docker/image cache. Each run's preflight and stop output in `0.10_cold_start.json` records `live_workers=0 pods_alive=0 pending_jobs=0` before t0 and the wait for the container to exit after the job (runs 2–3: ~25 s / ~19 s until `running=0`).
- Consequence: run 1 started from a **throttled** slot and included RunPod re-initializing the worker (throttled → initializing → idle → running; `delayTime` 269.4 s). Runs 2–3 started from an **idle** (scaled-down, image cached, container exited) slot on the same worker `80bn9jfb3f74tc` (`delayTime` 14.6 s / 8.7 s). Image pull is therefore included only in run 1.
- Code change: `scripts/pilot/infra_10/_common.sh` (`workers_alive`, `pods_alive`, `wait_zero_workers`) + README note.

## Interpretation of the delay

Formal start→READY exceeds the 60 s target because of run 1. RunPod reports that almost all of run 1's elapsed time occurred before the readiness job began execution (`delayTime` 269.4 s of 271.2 s; provider_delay_fraction 0.993). The readiness handler itself completed in <1 s in every run (0.28–0.35 s). During run 1 `/health` showed the slot `throttled` at submission and `initializing` ~3 min later, i.e. the host GPU was busy and RunPod had to (re)initialize the worker; during the earlier manual smoke RunPod explicitly reported waiting for RTX 5090 availability. Low RTX 5090 host availability is therefore an important contributor, but `delayTime` is a **provider-reported pre-execution delay** in general (queue, capacity wait, worker initialization, container start, other provider overhead); it must not be called GPU queue time as a whole, nor attributed entirely to container startup, from this evidence alone.
